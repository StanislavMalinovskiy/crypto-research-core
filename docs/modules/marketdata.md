# marketdata

- **Responsibility:** append-only raw observations and transaction payloads, recorded-swap normalization, immutable dataset snapshots, bounded point-in-time market observations, separated price/liquidity/USD-conversion facts and point-in-time token universes. Real provider adapters, stream-gap recovery and the remaining live-ingestion evidence facts are future F3 work.
- **Owned data:** `marketdata.raw_chain_events`, `marketdata.raw_transactions` (one provider payload per chain + transaction + provider with trusted-clock `received_at`/`admitted_at`/`ingested_at`), `marketdata.normalized_swaps`, `marketdata.dataset_snapshots`, `marketdata.dataset_snapshot_members`, `marketdata.price_observations` (swap-derived native price with quote asset; point-in-time index), `marketdata.liquidity_observations` (pool liquidity with raw reserves; point-in-time index), `marketdata.usd_conversion_facts` (immutable conversions with database-enforced references to both price observations and method version) and `marketdata.universe_snapshots` + `marketdata.universe_members` (fingerprinted point-in-time universes with recorded inclusion/exclusion). Raw identity includes provider; normalized identity is `(chain_id, transaction_value, event_locator)` and retains provider, raw digest and transformation version as lineage. Secondary indexes exist only for the documented point-in-time queries; the new tables are unpartitioned by explicit decision until spike-measured volume exists.
- **Public API:** the legacy `MarketDataApi` route synchronously replays a recorded dataset, finalizes an immutable snapshot and returns normalized observations bounded by window, cutoff and optional dataset fingerprint. It exposes immutable domain records, never JDBC, Jackson or provider types. V5–V9 fact-table operations use module-internal use cases; the separate versioned API path below exposes frozen revision evidence to signal/evaluation consumers.
- **Allowed dependencies:** `kernel::api`.
- **Transactions:** every raw observation commits through the existing raw-storage use case before a separate normalization transaction; parse failure therefore retains raw evidence. Dataset finalization is one short module-owned transaction after member selection.
- **Numeric/time contract:** quantities are exact integers; price is scale 18, liquidity scale 8 and confidence scale 4. Authoritative times are UTC `Instant` values normalized to microseconds before normalized-evidence comparison and persisted as `TIMESTAMPTZ(6)`.
- **Reproducibility:** snapshot content is sorted by normalized identity and hashed as algorithm-qualified SHA-256 using versioned UTF-8 length-prefixed fields. Content includes normalized values, raw digest lineage and transformation version; equal permutations reproduce the fingerprint and changed evidence or canonicalization does not.
- **Invariants:** raw and normalized evidence is immutable; equal replay is idempotent and conflicting evidence fails without overwrite; point-in-time queries have a total order and exclude observations after the declared cutoff; other modules never read market-data tables directly.
- **Non-goals:** live provider connectivity, gap recovery, provisional/finality handling, signal generation, wallet scoring, risk decisions, outcome valuation and EVM provider implementation.
- **F1/F2 readiness boundary:** [F1 provider research](../../openspec/changes/archive/2026-09-29-define-solana-data-provider-contract/tasks.md) is archived with provisional shortlist; original S1–S5/3.6 targets remain deferred/unverified, and production provider selection is unresolved. V5–V9 implement the F2 core-storage slice; [A1+A2](../../openspec/changes/archive/2026-10-01-version-market-facts-and-split-evidence/tasks.md) adds versioned evidence, not complete live readiness. A future approved F3 ingestion change must use forward-only migrations to add token-decimal evidence, provider-visible availability facts, and explicit quality status/policy/reason/source provenance before admitting live data. The V10 modeled-history label does not supply those live-ingestion facts. Missing inputs must remain explicit rather than fabricated.
- **Main tests:** pure validation and canonicalization behavior plus PostgreSQL 18.6 tests for V1/V2 schema ownership, raw-first parse failure, normalized retry/conflict, cutoff exclusion, total ordering, snapshot permutation and fingerprint sensitivity, and V5–V9 storage: exact raw transaction idempotency/conflict/batch (including opaque slash identities and a 10,000-row volume batch), price/liquidity observation idempotency and point-in-time windows, enforced USD-conversion lineage/immutability, universe point-in-time membership, and 1,001-member dataset/universe chunk boundaries with rollback evidence.

## Versioned evidence path

Forward V10 tables add `swap_revisions`, `price_revisions`, `liquidity_revisions`, `usd_revisions`, `v2_dataset_snapshots`, their ordered members and exclusions under the same `marketdata` schema. A canonical event/fact key can have multiple immutable source or derivation revisions; a same-revision content conflict fails. USD revision identity and database foreign keys pin both exact input price revisions. Existing V1–V9 rows, foreign keys, fingerprints and API reads retain their legacy meaning.

`MarketDataApi` exposes `replayVersioned`, exact `versionedFact` and `versionedObservations` reads, `finalizeVersioned`, and persisted `versionedSnapshotEvidence`, including the stored selection and canonicalization versions. The `explicit-revisions-v1` finalizer uses a short `REPEATABLE READ` application transaction to independently enumerate visible canonical keys in the declared scope. Every key must have one admissible revision or a justified exclusion with matching immutable evidence; a key with any admissible revision cannot be excluded. The stored fingerprint covers the canonical scope, knowledge cutoff, availability/selection policy, ordered revision members and exclusions, and coverage. Modeled history is labeled `HISTORICAL_MODEL`; `VERIFIED_REALTIME` obtains its cutoff at freeze and requires availability evidence. Both decision and evaluation batches stop above 10,000 visible keys or 20,000 visible revisions, independently, and process at most 1,000 rows per chunk. The read fetches at most a 20,001st revision to detect overflow before publication. Later commits and backfills cannot change an existing snapshot.

PostgreSQL regressions cover the populated V9 forward migration, exact USD revision foreign keys, revision coexistence and conflict, omitted/duplicate/forged dispositions, exclusion sensitivity, 1,001-member batching and rollback, late commits, concurrent equal retry, the 10,001st visible key, and the 20,000/20,001 visible-revision boundary. This path does not add a live provider or claim provider-wide completeness. See [Research reproducibility](../REPRODUCIBILITY.md).
