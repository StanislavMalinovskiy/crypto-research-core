### B4: new revision dimensions, legacy reads

Author paths: `RecordMarketFactUseCase.java`, `VersionedFactFingerprint.java`, `VersionedFactStore.java`, `JdbcVersionedFactStore.java`, `JdbcVersionedSnapshotStore.java`, optional marketdata-internal typed exclusion record; `MarketFactStorageIT.java` and `VersionedSnapshotStorageIT.java`. Preserve the original non-null derivation version exactly in both the hash input and existing persisted `derivation_version`; return the existing result's evidence-version value `EXPLICIT_REVISION_V2`. The versioned hash domain distinguishes the new identity algorithm, while derivation provenance describes the original transformation and is not repurposed as an identity-version field. No prefix, truncation, surrogate hash or capacity reduction is permitted: the existing full 128-character capacity remains usable. The result marker is explicit write evidence, not a persisted version column or a self-describing digest. Existing v1 rows remain exact-key readable and usable by frozen snapshots/USD references; no silent fallback aliases or bulk rewrite. Existing swap/USD identity algorithms are unchanged. New write retry uses the new version consistently; old recorded references are not regenerated. SQL snapshot retry reads component columns into immutable tuples; compare reasons/evidence as components, not string concat. No migration or schema changes are needed for this bounded repair.

Deterministic stored-version recognition: a small module-internal exact-key lookup returns immutable saved identity fields for price/liquidity: kind, chain, transaction, locator, asset, venue/pool, source identity, raw payload hash and original derivation version. Recompute candidate v1 using the unchanged legacy dimension concatenation and candidate v2 using separately named canonical fields. Exactly one candidate must equal the stored revision key: identify v1 or v2 accordingly; neither or both matches is an explicit integrity failure, never a guessed version from derivation text. The lookup can reuse existing query boundaries but must fetch actual stored asset/dimension; the public `VersionedFactEvidence` alone does not contain those fields and cannot prove tuple equality. This is recognition from recorded lineage, not a claim that a version column exists. Keep existing exact-reference read APIs and historical rows unchanged; test both saved versions and unmatched identity evidence. V10 revision keys and their foreign-key references are `VARCHAR(71)` with the `^sha256:[0-9a-f]{64}$` check, so a textual v2 key prefix is rejected as a no-schema alternative.

Before a new v2 price/liquidity insert, compute the corresponding v1 candidate and use the exact lookup. If a saved recognized v1 row has the same actual canonical tuple (kind, chain, transaction, locator, asset and venue/pool) and identity lineage, reject explicitly as a legacy-version conflict before any new row is inserted; equal or changed payload resubmission must not silently duplicate an already recorded fact. Do not alias, rewrite, return a v2 label for a v1 key, or manufacture a new revision merely for the encoding transition. A v1 row whose joined dimension string collides but whose actual asset/venue-or-pool tuple differs does not represent the same fact and must not block the valid distinct v2 write. Preserve normal v2 equal retries and content-conflict rejection. This guard applies to the upgraded write path, not a claim of online mixed-version deployment safety; older writers must not run concurrently as a migration strategy.
