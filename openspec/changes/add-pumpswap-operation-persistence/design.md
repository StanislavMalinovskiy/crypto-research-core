## Decisions

1. Add `persistPumpSwapOperations(RecordedBatch)` and `persistedPumpSwapOperations(String batchKey)` to the existing synchronous API. The write calls the real existing decoder, prepares bounded canonical rows outside the transaction, then invokes a separate proxied transactional publisher. It accepts no caller-decoded Result. Read returns Optional of an immutable stored-batch wrapper identifying storage version, original Result, batch key/first persistedAt and exact transaction/operation revision references. It reconstructs original source raw text from V5 rather than making another raw-payload store. Preserve ObjectProvider wiring and the old pure method. No public SQL/JSON/provider execution types.

2. Before publication, perform one bounded set lookup of at most128 raw keys and compare exact UTF-8 text/application hash, chain/signature/provider, observed slot, source time and all original clocks; no N+1 raw lookups or inserts. Repeat required equality within the publisher transaction against immutable raw parents. V5 does not prove finality or capture membership itself: caller metadata/session/sourceReference retain the decoder's trusted recorded-source contract and explicit provenance, not newly claimed independent admission. Keep finality/capture disposition/session/sourceReference in each immutable source binding. Reject missing/contradictory evidence; never repair stored raw or fetch it again.

3. New V14 owns four unpartitioned tables in marketdata: `pumpswap_transaction_derivations`, `pumpswap_operation_derivations`, `pumpswap_decode_batches`, `pumpswap_decode_batch_members`. Transaction derivations FK to V5's exact three-column key and retain raw digest plus source binding and complete canonical transaction result (without duplicated raw bytes). Their immutable content additionally seals the ordered operation revision keys and count, including zero, so another publication cannot append a new operation to an existing transaction derivation. Operation rows FK to exact transaction revision; retain canonical chain/signature/outer index/inner integer path/leg, revision key and complete canonical operation content. Batch rows hold versions/pins, original decoder fingerprint, sorted limitations, counts, storage fingerprint and first persistence instant. Membership holds batch FK, ordinal and transaction revision FK with uniqueness of revision within batch; operation membership resolves only the referenced transaction's sealed operation set. Publication and readback compare that exact set/count and reject additions/omissions, with no mutable expansion. Composite/FK consistency prevents operation chain/signature differing from its parent. No cascading delete or update. Natural identities use C collation for exact strings, nonnegative positions/leg, valid SHA-256 and bounded required text/bytes. Batch-member PK/unique keys support exact-batch lookup; one documented operation parent index supports retrieving operations for those members. No unrelated secondary indexes or partitioning.

4. Versioned canonical encoding uses ordered UTF-8 field names and byte-length-prefixed values, typed null/array/map framing, map-key sorting, exact decimal integer strings and canonical microsecond UTC instants. Domains are `pumpswap-tx-revision-v1`, `pumpswap-operation-key-v1`, `pumpswap-operation-revision-v1`, `pumpswap-content-v1` and `pumpswap-batch-v1`; outputs are `sha256:<lowercasehex>`. Canonical operation key fields are chain/signature/outer/entire inner path/leg only. Transaction revision fields are complete recorded source binding (provider, raw digest, session, reference, slot, finality, capture disposition and original clocks) plus decoder/schema/canonicalization versions and sorted source pins, storage encoding version. Operation revision fields are canonical key plus transaction revision. Derived statuses/amounts/proof paths belong to content, not revision identity. This makes changed output under the same inputs/version an immutable conflict rather than a new key. Session/reference differences create separate source-specific revisions deliberately, never different canonical operations. Batch grouping, limitation labels and the existing pure Result fingerprint enter only batch manifest identity/content. Never join opaque fields with a delimiter or hash ambiguous path strings.

5. Preserve all Operation fields exactly, including optional decimals, signed eventFacts, exact eventDeclaredFees/attributedFees, path lists, event digest, fee status/reasons and source reference. Canonical immutable TEXT serialization is permitted for nested evidence using baseline Jackson; encode arbitrary integer values without floating-point parsing, preserve sign/null/absence and reconstruct typed records. Do not use JSONB reserialization as authoritative equality. Store separate content digest and compare the complete canonical fields/content for retry; matching digest alone is insufficient. FK-to-V5 plus exact application comparison pins raw digest without altering V5 indexes. Bounded batched insert-first `ON CONFLICT DO NOTHING` followed by set read/complete equality retains first rows and times; no overwrite/upsert update.

6. One short marketdata application publication transaction (30s timeout; transaction-local statement/lock waits no greater than10s) atomically writes all prepared rows and manifest/membership. Parsing, canonicalization and provider I/O stay outside. At most128 sources,8MB/source,64MB total input/output and10,000 operations; rows chunk<=1,000, aggregate content bounded before SQL. Sort all insertion/read order by exact chain/signature/provider/session/source reference and numeric path/leg/revision tie-break to prevent order-dependent behavior. No automatic retry loop: transient DB error is explicit; caller equal retry is safe. Reads use exact batch key and bounded member/op set queries, at most129 members/10,001 operations to detect corruption/overflow, finite10s statement waits and64MB reconstructed output. Exact pinned immutable joins need no latest/freeze semantics. Empty batch is valid. Concurrent publishers use uniqueness resolution in separate real transactions; sorted writes reduce lock-order risk. Main peer advice on200–500ms remote RTT is a nonblocking reason to batch, not a managed throughput promise.
