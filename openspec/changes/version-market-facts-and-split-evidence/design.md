## Context

See [proposal.md](proposal.md). Today V2 dataset members identify only normalized event keys; V6/V7/V8 facts also use event-based keys, and V9 USD foreign keys name two price events without revisions. `FirstSignalEvaluationService` requires the run's sole dataset fingerprint to equal the accepted signal's fingerprint. The recorded integration fixture inserts future observations before finalizing that one dataset. Existing V1–V9 rows and exact v1 fingerprints/results are durable evidence; a new algorithm must not silently reinterpret them.

## Goals / Non-Goals

**Goals:**

- A versioned fact path that keeps canonical events, source observations and derivations distinct and lets a snapshot pin the exact immutable revision used.
- A decision snapshot finalized at the decision and a later evaluation snapshot, each with reproducible membership, content fingerprint, cutoff and availability status; one bounded snapshot can serve multiple signals.
- Exact old snapshot, signal, run, outcome and report readback and replay under their recorded versions after forward migration.

**Non-Goals:** provider ranking/arbitration, live adapter or finality/reorg design, full source-history backfill, new signal families or horizons, new trading latency/cost model, generalized temporal database, partitioning, another store, dependency or module edge. The minutes/hours/days manual operating game remains a separate R1 hypothesis; `1h` valuation does not assert acceptable entry delay.

## Decisions

### One change with internal A2-then-A1 task order

Use one integrated OpenSpec change. Versioned snapshot members cannot be implemented safely before exact revision keys and USD lineage exist, and a separately archived A2 without A1 would leave a new write/read path without the final dual-evidence admission rule. Implementation tasks first establish additive revision storage and compatibility, then freeze versioned snapshots, then expose versioned signal/evaluation behavior. Each step has PostgreSQL tests; no intermediate step is declared a completed product fix. `marketdata`, `signal` and `evaluation` keep their existing owners and only call `marketdata::api`/`signal::api`. `kernel` and the dependency DAG do not change.

### Revision identity, content and selection

Keep a provider-independent canonical event identity `(chain_id, transaction_value, event_locator)`; liquidity also scopes asset and pool. New fact kind and canonical dimensions, typed source-observation reference (V1 raw event or V5 raw transaction), source provider/raw digest, and transformation or conversion-method version form an application-derived, versioned revision key. For USD, both exact input price revision keys are part of its derivation key. A separate canonical content digest covers all persisted immutable fields including exact numeric values and declared availability status. Reusing one revision key with different content is a conflict; another source or version yields another immutable revision. Reject event-only selection when multiple revisions exist; the v2 snapshot caller proposes one exact revision per included canonical fact key under `explicit-revisions-v1`. The finalizer independently verifies complete coverage of the declared scope; an explicit list alone is not proof of completeness. This change does not invent provider preference. Canonical UTF-8 length-prefixed SHA-256, PostgreSQL microsecond normalization, exact decimals and bytewise `C` ordering follow the existing reproducibility contract.

Add module-owned revision tables for normalized swaps, price, liquidity and USD, plus v2 snapshot headers and typed revision members in forward migrations after V9. Keep all V1–V9 tables, rows, indexes, legacy FKs and readers; do not edit historical migration files or copy old rows into v2 with invented source availability. A versioned USD row has database-enforced foreign keys to both converted and quote **price revisions**; its source pair, method and value are immutable. New read APIs return revision identity and provenance without exposing JDBC or provider transport objects. The existing first-slice price/liquidity projection remains tied to selected normalized swap revisions; standalone fact revisions become selectable evidence but this change does not alter the `1h` valuation formula or silently switch its price source.

### Snapshot freeze: explicit stored membership

Compare two safe choices:

| Choice | Safety argument | Cost and decision |
| --- | --- | --- |
| Explicit immutable member list, as in current `dataset_snapshots` | Read exact revision IDs under one short `marketdata` `REPEATABLE READ` transaction, persist header and ordered members atomically. A write not committed when that transaction acquires its snapshot is invisible throughout selection; later replay reads stored members, not a query over current rows. | **Choose now.** Reuses an existing pattern; storage grows with selected members, so share each bounded decision/evaluation batch snapshot and measure actual size before optimizing. |
| Sealed admission epoch | A publisher/consumer barrier could prove all facts in an epoch committed before sealing and permit query-defined membership. | Safe only with a commit-safe seal protocol across all writers and revisions, recovery and cross-instance tests. It adds write-path coordination without measured need; defer. |

A pure `admitted_at <= cutoff` query or a sequence allocated before commit is **not** a safe third choice: a row timestamped 11:59:59 can be invisible to a 12:00 query and become visible on future replay after a 12:00:01 commit. `REPEATABLE READ` stabilizes one transaction, not historical re-execution. The chosen stored member list gives durable membership independently of later transaction visibility; `REPEATABLE READ` additionally keeps chunked selection within one consistent view.

The request declares an immutable selection scope: exact chain/asset/pool or venue filters where applicable, event/observation windows, fact kinds and versioned availability/exclusion policy. Within the same `REPEATABLE READ` freeze transaction, the finalizer independently enumerates the visible canonical fact keys in that scope from the versioned fact store, not just the caller's references. Canonical keys include fact kind and its dimensions, so a swap and its price are distinct facts. Every visible canonical key must have exactly one selected admissible revision or exactly one explicit exclusion with a policy-permitted reason and supporting immutable evidence. Missing, duplicate or contradictory dispositions, members outside scope and unsupported exclusions reject the entire finalization. An admissible newer liquidity fact cannot be dropped by omission or a generic caller-preference reason. Unknown/unusable availability is an explicit exclusion or rejection under the declared policy, never an invisible drop. This proves completeness only over visible stored facts in the declared scope, not provider or chain-wide completeness.

Persist the scope, included revision members, excluded canonical keys with reasons/evidence, coverage counts and policy version atomically in the manifest; all participate in the fingerprint and equal-retry comparison. Fingerprint members in total order `(observed_at, chain_id, transaction_value, event_locator, fact_kind, revision_key)` with bytewise text comparison and give exclusions a total canonical-key order. Completeness enumeration uses deterministic keyset chunks of at most 1,000 keys and stops with rejection on the 10,001st visible canonical key; selected references and exclusions are also bounded to at most 10,000 each. No full-history scan, hidden truncation or smaller scope is substituted. A valid bounded scope therefore has at most 10,000 dispositions, including exclusions. Equal snapshot identity retries compare all immutable header/member/manifest content; conflicts roll back atomically. These conservative bounds are admission controls, not a claim of measured capacity. The 10,000 limit is for decision/evaluation batches, not wallet history, which belongs to the separate offline research path.

For **verified realtime** v2 decisions, the market-data freeze operation acquires its PostgreSQL read snapshot and a trusted freeze instant in the same initial database read; it returns that normalized instant as the decision knowledge cutoff. The caller cannot supply an earlier decision cutoff and retrospectively claim that today's visible rows were known then. The signal uses the returned cutoff and frozen snapshot. A historical run may request an earlier modeled cutoff only in an explicitly labeled `HISTORICAL_MODEL` selection; it cannot report verified realtime availability. A fact must satisfy event/observation and source-availability rules for that selection. Unknown availability is not silently replaced with source event time or `admitted_at`. Evaluation freezes its own later snapshot and cutoff by the same rules. No provider I/O occurs in either transaction.

### Signal, evaluation and legacy version dispatch

Version the new evidence contract and canonical fingerprint inputs. The new accepted signal records the decision snapshot fingerprint, knowledge cutoff and selected source revision IDs; its identity derives from those immutable inputs plus the existing detector/risk/configuration evidence. The new run stores that decision fingerprint unchanged and an independent evaluation snapshot fingerprint and cutoff. Entry/horizon candidates are read only through the evaluation snapshot and the existing strictly-post-availability/`1h` rules. Run/outcome/report identities include the two evidence references and exact chosen observation revisions; missing evidence remains a counted `UNPRICED` outcome. Use new module-owned v2 signal/evaluation tables with dedicated, required `decision_dataset_fingerprint` columns, and a separate required `evaluation_dataset_fingerprint` on v2 runs. Outcomes/reports resolve both through their v2 run and expose both in provenance. Existing legacy tables and their `dataset_fingerprint` columns retain their original single-dataset meaning and constraints; v2 rows are not inserted into them. Never encode a decision or evaluation identity in the old column, alias the two new fields into it, or require readers to infer its meaning from a version flag. Keep contract-version and exact revision references explicit on the new path. No cross-module database FK is added from `signal` or `evaluation` to `marketdata`.

Legacy snapshot, signal and evaluation read/replay dispatches by persisted version and uses the original v1 canonicalization, ID and valuation logic, including the recorded legacy dataset membership. It does not recompute old fingerprints using current normalized revisions. New authoritative publications use the dual-evidence path; legacy callers can read and verify already persisted evidence but cannot silently publish a new single-dataset result as if it met the new point-in-time claim. The old recorded fixture remains as a compatibility regression, explicitly labeled legacy. If the old algorithm's recorded behavior included a preloaded future dataset, its historical result is reproduced as legacy evidence, not relabeled as a valid new chronological decision.

### Transaction and verification ownership

Raw-first replay still commits raw evidence before a separate `marketdata` normalization/revision transaction. Each fact revision insert is an owned short transaction with database uniqueness and equal-content comparison; USD input price revisions must exist before its insert. Snapshot finalization is one short market-data transaction, including all header/member writes. `signal` retains candidate-first and accepted-decision transactions. `evaluation` reads public APIs before one short atomic run/outcome/report transaction. No module directly queries another's tables, no provider call enters a transaction, and no queue or unbounded retry is introduced.

Behavioral RED uses a compilable v2 route before the new persistence or semantics are implemented. Minimal v2 request/result declarations and temporary adapters delegate to the real legacy market-data replay/finalization/read, signal detection and evaluation operations; the evaluation adapter maps the versioned decision fingerprint to legacy `evaluate` and carries the separate evaluation fingerprint without using it. An internal v2 fact-use-case adapter similarly delegates to current fact store/read operations. This bridge is only a measured baseline for modeled historical fixtures, with legacy-labeled evidence and no verified-realtime claim; it is replaced behind the **same** test-facing route for GREEN. The chronological PostgreSQL assertion expects `PRICED` using a later evaluation snapshot but observes `UNPRICED` from the legacy decision-only snapshot. The revision coexistence assertion expects a second stored swap/price revision but observes `NORMALIZATION_FAILED` for the second swap and `MarketFactConflictException` for the second price. These are executed behavioral failures, not compilation, discovery, absent-table or canned-failure evidence. Freeze those assertions after RED, keep legacy compatibility tests separate, and do not rewrite either route's expected behavior to obtain GREEN.

Further PostgreSQL acceptance assertions cover: (1) an uncommitted revision across freeze followed by an earlier-timestamp commit leaves old members/fingerprint unchanged; (2) late backfill and second valid revision produce a distinct new snapshot while old pinned selection stays exact; (3) USD rejects a missing/mismatched converted or quote **revision**, not merely a missing event; (4) equal/concurrent retry yields one complete fact/snapshot/run and conflicting same-revision or aggregate content rolls back; (5) a populated pre-migration PostgreSQL V1–V9 fixture has identical exact old IDs, fingerprints, selected rows, priced/unpriced outcomes and ordered report content after migration and legacy replay. Pure tests cover canonical encoding/order and version dispatch; migration, visibility and FK assertions use PostgreSQL 18.6 Testcontainers. Run `ApplicationModules.verify()` through the complete gate.

Before implementing completeness checks, another frozen PostgreSQL RED uses the same v2 finalization route and a declared scope with two visible liquidity events but only the older revision supplied. The minimal legacy-delegating baseline finalizes successfully; the required assertion is an explicit incomplete-selection rejection with no persisted snapshot aggregate. GREEN must validate coverage through the same route and preserve that assertion. Also test permitted exclusions, unjustified reasons, duplicate dispositions, scope/exclusion fingerprint sensitivity and the 10,001st visible key. Main runs intermediate complete gates after task sections 2 and 3; Builder supplies targeted evidence. An intentionally pending section-3 RED at the first gate is reported as a failure and keeps that checkpoint incomplete until rerun passes, without skipping or changing tests. Keep the bridge minimal.

## Risks / Trade-offs

- [A reproducible but incomplete caller-selected list changes a latest-observation decision] → Verify scope coverage in the freeze transaction, require one inclusion or justified exclusion per visible canonical key, fingerprint the full manifest, and establish an omitted-visible-fact RED before implementing that validation. Cap enumeration as well as writes; a full wallet-history export is outside this path.

- [More snapshot member rows and hashing work] → Cap and chunk first-slice snapshots, share by bounded batch and benchmark actual writes/reads before considering epochs; do not claim an unmeasured scaling failure.
- [Concurrent freeze/retry may encounter uniqueness or isolation aborts] → Fail atomically, then resolve an equal persisted snapshot or return explicit conflict through a finite retry; never recompute an existing identity from current rows.
- [Old rows lack proven availability/revision provenance] → Keep exact legacy read path and mark any later rederivation as a distinct modeled/new revision; no silent backfill or upgraded realtime claim.
- [Version split can make run replay ambiguous] → Persist contract version and both evidence references; keep golden pre-migration readback/replay tests.
- [Post-migration rollback to old application cannot consume new v2 evidence] → Stop v2 writes and use the old application only for legacy reads while preserving additive v2 rows; repair forward rather than dropping or down-migrating evidence.

## Migration Plan

1. Before implementation, capture a populated V1–V9 PostgreSQL baseline with exact legacy snapshot members/fingerprints, signal IDs and priced/unpriced run/outcome/report fields and ordered content. Freeze expected values in tests; do not construct the expected result by the new code after migration.
2. Apply additive module-owned Flyway migrations after V9: revision tables and exact USD price-revision FKs in `marketdata`; v2 snapshot headers/members plus exclusion/coverage manifests; new owned v2 tables in `signal` and `evaluation` with separate required decision/evaluation fingerprint columns. Preserve old rows, keys, `dataset_fingerprint` semantics, constraints and legacy FKs in place. Introduce query-backed indexes only.
3. Verify old readback and recorded-version replay bit-for-bit in durable fields before enabling new publication. Exercise empty and populated DB upgrades, exact old fingerprint/hash dispatch, FK integrity, 1,001-member chunk boundary and rollback of a late member/report failure.
4. Enable the new versioned replay/finalization, then dual-evidence signal/evaluation flow. No new provider or paid probe is part of this deployment. On failure, stop new publication, retain all evidence and apply a forward correction; never rewrite V1–V9 or delete v2 rows to make old binaries appear compatible.
