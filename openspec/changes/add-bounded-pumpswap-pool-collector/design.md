## Decisions

1. Use JDK HTTP/WebSocket adapters inside `marketdata.infrastructure`, finalized `logsSubscribe` per configured pool and finalized `accountSubscribe` for its pool/two vaults/two mints. Fetch full `getTransaction` JSON for each signature; bounded `getTransactionsForAddress` full pages are proposed for transaction-only reconnect recovery. Preserve success/error state and all actual JSON, not a parsed economic summary. Initial/reconnect finalized account reads establish new state observations, not historical state recovery. Pure polling was considered but misses subscription intent and changes freshness/coverage; gRPC is deferred because its SDK and separately billed byte stream expand this first slice. Published endpoint support is not a successful live subscription test.
2. Start with a supplied pool/account allowlist, no discovery. Validate chain/address syntax and pinned owner/program/account linkage using finalized metadata; unresolved linkage blocks that pool. Configuration pins PumpSwap program, token programs, pool, vaults and mints plus the source/version of the linkage proof. No pool binary decoder is assumed: supplied finalized metadata/proof must identify vault/mint linkage; checking program ownership alone cannot prove that mapping. Budgeted current account reads verify declared owners and available SPL/Token2022 mint/authority fields; unsupported layouts remain unresolved, never guessed by offsets. JDK asynchronous callbacks hand off to bounded synchronous processing; no provider/async types cross `marketdata::api`. Add one synchronous start/stop/status boundary in the existing API with ordinary immutable records. No new graph edge or ADR decision.
3. Add forward-only marketdata migrations after the current maximum version: session/config fingerprint, PostgreSQL expiring lease, pending signature dispositions, raw account snapshots and gaps. Session identity is owner-supplied UUID plus immutable versioned configuration fingerprint; natural transaction identity is the existing chain/signature/provider tuple. State primary key is chain/provider/account/context-slot/application SHA-256 of exact UTF-8 notification account-result text. Duplicate state content keeps first times; differing same-slot content is retained as ambiguity, not event ordering. All identity components use bytewise equality; ordering is slot, account/signature and digest as immutable tie-breaks, never callback order. Only indexes needed for session status, pending work, gap range and per-account state reads are introduced.
4. Claim the session with an expiring database lease committed before provider I/O; only its current holder writes checkpoint transitions. Use short owning application transactions: raw write first, then disposition/checkpoint; crash between them is retried against immutable raw storage. A checkpoint references actual committed raw/disposition keys, not merely the highest observed slot. PostgreSQL concurrency stays at one writer initially. Store exact notification/fetch provenance and clocks separately; no mutation of V1–V12 or existing snapshots.
5. Reconnect opens a durable gap before re-subscription. Recover transactions back to the previous committed signature boundary, with overlap/dedup and finite pages; out-of-order/missing boundary/nonadvancing cursor remains unresolved. Account snapshots never supply missed states or exact pre/post reserves. Status counters derive from durable dispositions, not metric attempts. Queue overflow closes transport and records an unresolved interval; process crash is evidenced by an unfinished session/expired lease on restart.

### Owner-authorized first-window envelope

First-window configuration: exactly 3 supplied pools, at most 15 distinct account subscriptions and 3 log subscriptions; one connection, one RPC in flight, 2 request starts/sec; queue 1,000 notifications and 16,000,000 UTF-8 bytes; one message <=2,000,000 bytes, HTTP response <=8,000,000 bytes. Request/connect timeout 10s; at most 2 transient retries with 1s/3s backoff and bounded Retry-After; at most 3 reconnect attempts. Owner window <=24 hours from the recorded UTC start, ending earlier at any cap or configured billing-period boundary. Proposed first allowance: 20,000,000 billable subscription bytes including control/error/fragment/close allowances, 150,000 RPC/control CU, at most 3,750 RPC starts including retries, 1,000,000,000 total HTTP/WSS received bytes and 1,200,000,000 retained bytes. HTTP bytes are not charged the WSS byte rate; every method also consumes its CU allowance. Each reconnect recovery <=10 pages/pool and 300s within original totals. These are configurable first-window values, not permanent product maxima, throughput promises or permission for expansion. Reserve a complete possible message before requesting the next bounded fragment and close early enough to retain shutdown/in-flight headroom; do not discard already received billing bytes from accounting. A client cannot prove a server-side billing ceiling for unsolicited/buffered traffic: charge known bytes, preserve conservative unreconciled reservations, disclose unknown provider-side excess, and rely additionally on the OWNER_REPORTED account cap rather than claim a mathematically guaranteed invoice. CPU/DB work remains bounded; one writer cannot exceed the existing datasource pool.

Monthly authority is the current OWNER_REPORTED $15 account limit, approximately 28.6 million CU, with reported reset 2026-11-01; actual cap/alerts and unused balance have not been independently observed. Require a configured non-negative starting-month CU/cost baseline (OWNER_REPORTED or independently observed), billing period identity/end Instant, and reserved allowance for other account activity; absent/unknown baseline blocks connecting, never assume zero. Durable month-accounting identity is shared across sessions/restarts. Atomically reserve the whole first-window 800,000 subscription CU plus 150,000 RPC/control CU against remaining monthly authority before connection; known usage and conservative outstanding reservations cannot be refunded merely by crash, session replacement or an unobserved dashboard reset. Unknown externally concurrent account usage requires reserved headroom or an exclusive allocation. Stop when either exact cost or CU ceiling is exhausted; initial current-period whole-CU cap is min(28,600,000, floor(15*1,000,000/0.525)) = 28,571,428 CU, before baseline/other reservations. Use integer hundredths of CU (0.04 CU/byte) and exact decimal USD rate; monetary comparison is unrounded, displayed USD rounds upward at declared scale. All limits/rates participate in immutable configuration. No automatic Nov1 reset/relaunch; a later owner change updates explicit authority/configuration, never silently expands the current window. Measure actual subscriptions/RPC/control usage after the first day or earlier stop; continuing or expanding requires the owner, not a new session identifier.

Three owner-supplied pool inputs and bounded finalized metadata verification are recorded in the verified-status section below. The preserved first-five verifier configuration supplies cohort token mints, not a pinned three-pool/two-vault/two-mint mapping; historical diagnostic fragments do not prove current finalized pool ownership. No outcome/rate-based selection or new raw scan is authorized by this plan. Accept exactly three owner-supplied pinned mappings, or a separately approved deterministic mapping from retained source evidence, then perform only budgeted finalized linkage validation before subscriptions. Unresolved linkage blocks its pool rather than replacing it; the observed first-run checks do not establish atomic same-slot state or healthy live coverage.

Linkage-proof input is an explicit operator-supplied immutable finalized metadata record: chain, context slot, pool address/program owner, ordered base/quote vault and mint addresses, each token-program owner, exact source payload and SHA-256, verifier/source version and declared verification provenance. Validate field equality with the allowlist, payload hash, finalized provenance and supported metadata structure before any subscription. This is supplied linkage evidence, not collector-derived binary pool decoding: the operator is responsible for the mapping proof, while budgeted live reads verify current declared owners and supported vault mint/pool-authority metadata. Unknown or conflicting proof fails closed; fixtures cover mismatch/hash/finality/owner/mint/authority failures. No economic-layout offsets are inferred. Resolve stored raw transaction first-observation clocks on equal redelivery; never weaken the existing raw store's immutable-time comparison.

Exact raw boundary: existing transaction storage receives the exact UTF-8 `getTransaction` result-subtree text containing the complete transaction evidence, not the JSON-RPC envelope whose request id changes. State digest/storage uses the exact account-result subtree text with context retained separately. Locate these source spans without reserializing JSON. Preserve complete exact fetch/notification envelopes separately in capture provenance/dispositions (credentials excluded); changing transport id does not create a transaction-content conflict, while changed result bytes do. Null/error responses have explicit dispositions and retained envelopes, not synthetic transaction rows.

### Capacity and cost assumptions

Let P be pools, t finalized transactions per pool per day, a account notifications per pool per day, bT/bA average retained bytes, H full history pages/day, B all billable WebSocket payload bytes/day and C control/read CU/day. Estimates: RPC starts/day = P*t + H + initial/reconnect reads; CU/day = 40*P*t + 100*H + 0.04*B + C; raw bytes/day approximately P*(t*bT+a*bA), plus notifications/errors/envelopes. P/t/a/bT/bA/B/C are unmeasured inputs, not source facts. [getTransaction](https://www.alchemy.com/docs/chains/solana/solana-api-endpoints/get-transaction) is 40 CU; [full history](https://www.alchemy.com/docs/chains/solana/solana-api-endpoints/get-transactions-for-address) is up to 100 transactions/request and 100 CU/request. Hypothetical H=1,000 costs 100,000 CU/day = $0.0525/day or $1.575/30 days at [published](https://www.alchemy.com/pricing) $0.525/million CU. [WebSocket billing](https://www.alchemy.com/docs/reference/solana-subscription-api-endpoints) uses [0.04 CU/byte](https://www.alchemy.com/docs/reference/compute-unit-costs): decimal 1GB/day = $21/day, $630/30 days, separately from RPC/storage. Account-specific allowances and actual load remain unverified; unknown total blocks paid launch. WebSocket is proposed first to satisfy live subscription scope without a new gRPC SDK; small allowlists and stops are essential. If measurements exceed the new approved budget, stop and replan an explicit RPC-polling scope with disclosed freshness/state losses; do not silently substitute.

Owner's approximate 24 MB/day is not a safe $15 monthly allocation: 24,000,000*0.04 = 960,000 CU/day, 28,800,000 CU/30 days, $15.12 before RPC/control. First-window 20 MB plus 150,000 RPC/control CU gives 950,000 CU/day = $0.49875; 30-day hypothetical repetition gives 28,500,000 CU = $14.9625, only if no prior/other usage. Oct7 to Nov1 is 25 calendar days, not an automatic 30-day grant: a hypothetical 25-window total is 23,750,000 CU = $12.46875 before existing account usage, but only the first 24-hour window is currently authorized. At 40 CU/getTransaction the RPC allocation permits at most 3,750 such calls only when no controls/history/retries consume it; getAccountInfo costs 10 CU and history costs 100 CU, so actual transaction capacity is lower. No volume has been measured. gRPC remains excluded; its separate starting $75/TB price cannot be used for WSS. The exhausted earlier $3/15GB attempt is not a new budget. Measure PG table/index/WAL size and retention/restore needs in the authorized sample; no automatic raw deletion or assumption that provider reload/Account Archive will recover all state.
