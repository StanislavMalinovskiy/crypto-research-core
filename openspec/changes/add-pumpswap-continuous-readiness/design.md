3. Admission is an application-owned <=10s transaction with local statement/lock timeout<=10s. Manual admission and enrollment share one transaction-scoped PostgreSQL advisory provider lock, acquired FIRST before any admission row lock, using one common implementation in assigned JdbcCaptureStore: `pg_advisory_xact_lock(1129464656, hashtext(:provider))` for the exact already-validated `alchemy` identity; the fixed namespace is not allocation identity and collisions only conservatively serialize. Binding existence is a separate SQL statement AFTER acquiring the common lock, so its fresh READ_COMMITTED snapshot sees preceding enrollment. Hold the lock through binding check, period reservation and session commit; both manual and enrollment paths use the same key/order. Existing deployment: provider advisory lock -> deployment row lock -> existing period row lock/reservation. Initial enrollment: provider advisory lock -> create/verify required period FK parent -> insert/lock deployment -> lock/reserve period -> create/link session+segment; the leading shared lock serializes the FK bootstrap too. The V13-absent legacy guard remains unchanged. Wait failure is bounded by local10s statement/lock timeouts, observed<=15s, no retry/reservation/provider work. Check exact immutable equality, lease, global end/count and cumulative remaining resources; reserve full segment limits in all dimensions and existing period CU once; create/link session and segment atomically before provider work. Use checked exact integer CU hundredths and existing exact decimal cost functions, never floating-point or down-rounded authority. Operator supplies finite allowances; team adds no arbitrary cumulative cost/duration/count ceiling or new expense. Existing single-segment finite transport/queue/rate/retry ceilings remain.

An enrolled provider accepts only its immutable current allocation and linked exact segment under the current deployment fence; unbound historical legacy behavior remains unchanged. 5. One bounded coordinator uses a PostgreSQL deployment lease committed before I/O and the existing segment lease/writer fence. Claim/heartbeat/cursor/seal/completion transitions require exact holder+generation+unexpired lease. On losing fence, shut down owned provider admission; do not retry indefinitely or reacquire expired ownership to claim success. In one process actual coordinator+writer exit must precede seal/release/successor; across crashes, takeover uses expiry/new generation and authoritative old-holder writes fail. ## Risks / Trade-offs

- Full segment reservations can strand allowance after short/crashed segments -> intentional conservative no-refund; distinguish estimates/reservations/billing and let owner choose finite allocations, never silently increase them.
- Post-seal decode delays derived visibility and creates planned nonoverlap -> explicitly no low-latency/continuity claim; bounded cursor/backlog and retained boundary gaps, not arbitrary queue/recovery framework.
- Lease expiry is not proof of actual process death -> retain active ownership until exit, database fences reject stale writes; unavailable closing never fabricates seal/successor.
- One provider allocation binding is not general multi-account support -> fail closed on rename/period mismatch; any owner-authorized rebinding/reopen requires separate future contract.
- Existing V14 artifacts remain unarchived -> reuse exact verified behavior and reconcile conditional collector exception at future authorized sync/archive, no accepted-spec mutation now.
